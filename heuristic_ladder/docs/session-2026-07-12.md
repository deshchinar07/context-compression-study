## 1. Understanding the harness (morning)

### Exploration order

We mapped the repo and agreed on a dependency-ordered reading path:

1. `README.md` — scientific claim (timing → selection → ceiling)
2. `blocks.py` / `tokenizer.py` — state + budgets
3. `data.py` — examples and multi-objective packing
4. `policies.py` — the ladder itself (H0→Oracle)
5. `agent.py` — fixed ReAct environment
6. `runner.py` / `aggregate.py` / `cli.py` — orchestration

Shortcut for the thesis only: README → `policies.py` → `agent.py` → `metrics.py` →
`aggregate.py`.

### Data model

- **`Paragraph`**: one candidate passage (`idx`, `title`, `text`, `is_supporting`,
  `objective_idx`). `is_supporting` is gold evidence; only the **Oracle** may read it.
- **`Example`**: one task with a self-contained paragraph pool, questions, answers.
- **Three datasets** (HotpotQA, 2Wiki, MuSiQue) normalize to the same JSONL shape but
  differ in pool size (~10 vs ~20), reasoning style (comparison vs bridge vs composed
  hops), and distractor difficulty.

### Why a ~10-paragraph pool instead of MEM1's full Wikipedia?

| MEM1 / Search-R1 | This harness |
|------------------|--------------|
| Dense index over ~20M Wikipedia passages | BM25/e5 over each example's bundled pool |
| Retrieval failure is a real factor | Gold is always in the candidate set |
| No known finite gold set among arbitrary chunks | `is_supporting` labels map exactly |

**Design justification:** The study isolates **compression policy** (timing vs.
selection), not retrieval quality. A bounded pool:

1. Makes the **Oracle** definable (perfect selection among known gold+distractors).
2. Holds retrieval **fixed** across rungs so H0→Oracle gaps are causal.
3. Runs locally without a 20GB index.

**Cost:** Absolute scores are not directly comparable to published full-corpus MEM1
tables. The harness addresses this with **in-harness MEM1** (`baselines/mem1.py`), not
by assuming the small pool is harmless.

## 2. Backbone and endpoints

### "Local frozen Qwen" and the no-caveat tier

- **Frozen** = same weights, temperature 0, deterministic continuations.
- The harness is an OpenAI-compatible **client** (`llm.py`); "local" means pointing
  `--base-url` at a server on your machine.
- **Two different "no-caveat" phrases** in the README:
  - **Backbone fidelity** (hosted DeepInfra vs local full-precision vLLM)
  - **Retrieval fairness** (in-harness MEM1 vs published table overlay)

### macOS reality

- vLLM/TGI (true no-caveat backbone) = **CUDA-only**.
- Ollama / LM Studio / MLX work locally but are typically **quantized** → smaller
  fidelity caveat remains.
- **Practical recommendation:** DeepInfra for development; rented CUDA + vLLM for final
  pristine numbers.

## 3. Experimental design debates (afternoon)

### Is comparing to MEM1/PEEK worth it?

**Yes — it is the thesis**, not an add-on. Internal ladder gaps are clean regardless;
the external question is whether RL-trained folding beats training-free heuristics.

- **Priority:** in-harness MEM1 ≫ transcribing published tables (permanently caveated).
- **Unfixable confound:** learned method = policy **plus** trained backbone; you compare
  whole systems and disclose the backbone difference.

### "Can we use the 20GB index and average over many examples?"

**No for fairness.** Averaging reduces **noise**, not **bias**. Matching retrieval
scope removes the confound; averaging does not.

Going full-corpus also **breaks the naive Oracle** (arbitrary chunks lack clean gold
labels). That motivated the corpus-scope design below.

### Can we use full index without breaking the Oracle?

Three options were discussed:

| Approach | Oracle survives? | Realistic retrieval? | Issue |
|----------|------------------|----------------------|-------|
| **Gold injection** | Yes | Partially | Forces recall=100%; hides retrieval failure |
| **Title-match labeling** | Yes | Yes | Coarser labels; needs aligned Wikipedia dump |
| **Oracle-given-retrieval** | Yes (conditional) | Yes | Ceiling = perfect selection *given retriever* |

**Decision:** Primary design = **title-match + Oracle-given-retrieval**, report
**gold-retrieval recall** separately. Gold injection = optional supplementary condition
only.

### Publishable outcomes (either direction wins)

- **Heuristics ≈ MEM1:** training buys little once budget-aware; field should target
  H3→Oracle headroom.
- **MEM1 ≫ H3:** learning earns its keep on **selection**; report % of H3→Oracle gap
  closed and cost-normalize.

### Workflow tiers (agreed)

1. **`pool`** — dev + clean-Oracle primary (not throwaway).
2. **`union`** — local realism (~66k passages for HotpotQA), runnable on Mac today.
3. **`kilt`** — full Wikipedia FAISS/e5 (20GB tier), GPU box + prebuilt index.

## 4. Implementation (evening)

### Stage 1: corpus retrieval architecture

**Goal:** Same agent, policies, Oracle, metrics, and CLI — switch retrieval tier via
config only.

#### New / modified modules

| File | Change |
|------|--------|
| `ladder/corpus.py` | `build_union_corpus`, `CorpusIndex`, `build_corpus(source, …)` |
| `ladder/scoring.py` | `LexicalScorer.index_corpus`, `ScorerFactory` (build IDF once) |
| `ladder/agent.py` | `retrieval_scope`, title-match labeling at retrieval time, `gold_titles_*` fields on `RunResult` |
| `ladder/runner.py` | `_get_corpus` with cache; build once per (dataset, split) or once globally for kilt |
| `ladder/cli.py` | `--retrieval-scope`, `--corpus-source`, `--corpus-index-dir` on `run` and `run-baseline` |
| `ladder/baselines/mem1.py` | Same corpus scope as ladder; title-based recall accounting |
| `ladder/aggregate.py` | `gold_recall` column; `scope=` in group headers |
| `tests/test_corpus.py` | Offline tests: dedup, title labeling, Oracle-given-retrieval, recall |
| `README.md` | "Retrieval scope" subsection + three-tier workflow |

**Verified on real data:** HotpotQA 7,405 examples → 66,581 union passages; title
match and recall plumbing correct.

#### Stage 2 scaffold: KILT / 20GB

| File | Change |
|------|--------|
| `ladder/kilt.py` | `FaissRetriever` + `build_kilt_corpus(index_dir)` — loads `index.faiss` + `passages.jsonl` |
| `CorpusIndex` | Accepts **injected** `retriever` / `scorer_factory` so FAISS backend plugs in without agent changes |

**Not yet tested** against a real index (building ~21M e5 embeddings is an off-box GPU
job). Code fails loudly with actionable errors if deps or paths are missing.

#### Central config entry

| File | Purpose |
|------|---------|
| `run_experiments.py` | Single CONFIG block + `MODE`; documents all CLI equivalents and tier semantics |

**Design principle:** Changing `RETRIEVAL_SCOPE` / `CORPUS_SOURCE` / `CORPUS_INDEX_DIR`
in one file (or three CLI flags) is the **only** change needed to move pool → union →
kilt. Policies, Oracle, metrics unchanged.

### Fairness invariants preserved

- Only Oracle reads `Block.is_supporting` (now set by title match under corpus scope).
- Same retriever index shared across all rungs and (when configured) MEM1 baseline.
- `pool` remains default — existing behavior untouched.

## 5. Design decision summary

| Decision | Alternatives considered | Why we chose this |
|----------|----------------------|-------------------|
| Bounded pool as default | Full Wikipedia from day one | Oracle + causal decomposition require known gold set |
| In-harness MEM1 vs published overlay | Only overlay published numbers | Overlay is permanently confounded; in-harness cancels retrieval scope |
| Union corpus before KILT | Skip straight to 20GB | Test realistic retrieval locally; validate gaps before GPU investment |
| Title-match labeling | Gold injection | Keeps retrieval failures honest; injection hides recall errors |
| Oracle-given-retrieval ceiling | Absolute Oracle on full corpus | Honest ceiling under realistic retrieval; recall reported separately |
| `ScorerFactory` + corpus cache | Rebuild index per example | 66k+ passages × thousands of examples would be unusable |
| `run_experiments.py` | CLI only | One place for all knobs + documented run commands |
| DeepInfra first | Local MLX/Ollama immediately | Zero setup; cents per pilot; caveat acceptable for dev |
