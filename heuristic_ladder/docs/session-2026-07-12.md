## 1. Code understanding

### `data.py`
- `_serialize` / `_deserialize`: JSONL cache of normalized `Example`s (download once).
- `build_multi_objective`: shuffle + chunk into N independent questions sharing one
  paragraph pool and budget. **Not** similarity matching; **not** multi-hop
  dependence. “Multi-objective” = N goals in one episode under shared compression
  pressure (MEM1-style), not “answer A needed for question B.”

### `retriever.py`
- Per-example BM25 over that example’s pool only; identical for every rung.
- `_WORD` / `tokenize`: lightweight alphanumeric tokenizer for retrieval scoring
  (separate from the Qwen budget tokenizer).
- `k1` / `b`: TF saturation and length normalization in Okapi BM25.
- BM25 does **not** find gold answers; it ranks by lexical overlap. Gold is for
  metrics (`answers`) and Oracle-only (`is_supporting`).

### `policies.py` (refactor)
- Removed `CompressionPolicy` inheritance; H0–Oracle are standalone classes (OK to
  repeat the evictable-evidence filter for readability).
- `agent.py` types policies as `Policy = Union[H0, H1, H2, H3, Oracle]`.
- Policy + corpus tests still pass.

### H3 summarizer
- `Summarizer` in `summarizer.py`: query-focused rewrite on the **same frozen
  backbone** as the agent (default ≤40 words). Cost counted in the shared usage
  meter. Not a separate extractive model.

## 2. Design note A — lexical vs semantic selection (important)

H2/H3 pick the `victim` via `scorer.score(...)`. Default scorer is **lexical BM25**
(`LexicalScorer`), by design: training-free, dependency-free, deterministic.

Semantic relevance is often better when wording diverges (“birthplace” vs “born
in”). The harness already supports it: `--retrieval e5` swaps **both** retrieval
and the H2/H3 selection scorer to `intfloat/e5-base-v2` (Search-R1/MEM1-aligned).

**Carry forward:** default stays lexical; treat e5 as a **sensitivity /
paper-aligned** mode, not necessarily a replacement for the primary ladder.

---

## 3. Design note B — percentage-budget “H4”?

Idea: compress when context hits fixed % of budget (50% / 75% / 90%), not only when
about to overflow.

**Verdict:** good experiment, **weak as a primary ladder rung.** Percentage
triggers are still a **timing** knob (more aggressive than H1). Putting that after
H3 as `H4` confounds schedule aggressiveness with H3’s selection++. Prefer a
**timing-schedule ablation** with selection held fixed (H2 or H3 rule), parallel
to the e5-vs-bm25 sensitivity on selection. Early compression can help or hurt
(frees budget vs discards evidence before later needs are known).

---

## 4. Design decision summary

| Decision | Alternatives considered | Why we chose this |
|----------|----------------------|-------------------|
| Lexical BM25 as default H2/H3 scorer | Always use e5 semantic | Training-free primary ladder; e5 as sensitivity / paper-aligned mode |
| %-budget compression as timing ablation | Add as primary H4 rung | Keeps H0→Oracle gaps single-knob; schedule aggressiveness is still timing |
