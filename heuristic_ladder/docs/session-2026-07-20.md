## 1. Empty predictions (blocker)

**Symptom:** First pool pilot (`limit 20`) had **93/200 empty** preds (~46%).

**Cause:** Model burned `max_tokens` inside `<think>` and never emitted `<answer>`. Force-answer cue was ignored; `_clean_answer` stripped think → `""`.

**Fix** (`agent.py`, `llm.py`, `prompts.py`):
- Assistant prefill `"<answer>"` on commit-nudge + force-answer paths
- Stronger force/commit cues

**Result (pilot v2):** **0/200 empty**; voluntary answers 66 → 168.

## 2. Pool Hotpot single-obj (n=200)

`results/pool_hotpot_n200.jsonl` — budgets 256 & 512, all rungs.

### B=512 (primary)

| H0 | H1 | H2 | H3 | Oracle |
|---|---|---|---|---|
| 0.30 | 0.42 | 0.47 | 0.49 | 0.50 |

Gaps: timing **+0.12** → selection **+0.05** → selection++ **+0.02** → headroom **+0.01**.  
H3 ≈ Oracle (~98%). **Timing is the main gain.**

### B=256 (caveat)

H3 **beats** Oracle (0.40 vs 0.31). Not a scoring bug: under tight budget Oracle hard-deletes and often **retrieves gold then keeps 0 supporting** (120/200); H3 summarizes and answers earlier. Treat B=256 as stress, not the ceiling story.

**Decision:** Prefer budgets ≥512 for headline tables. Full 7k Hotpot **not** required; n=100–200 is the plan default.

## 6. Current takeaway

1. **H0→H1 (timing)** is the robust finding (pool + union + multi-obj).  
2. **Selection (H1→H2)** helps some; **H3 (summarize/anchors)** rarely wins over H2 here.  
3. Oracle is a clean ceiling mainly when budget binds but isn’t pathological (favor **B=512**).  
4. Pool was not lying: union keeps the same decomposition direction with lower recall and more headroom.
